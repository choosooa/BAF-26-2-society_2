## 3. 실험 규칙
- 모든 비교는 **같은 fold(사상 단위 GroupKFold 4-fold)·같은 LightGBM 파라미터·같은 seed(42)**. 피처 효과와 튜닝 효과를 섞지 않음
- 채택 기준: 기준 대비 OOF RMSE 0.0005 이상 감소 **그리고** 4개 fold 중 3개 이상 개선
- 기록 방식: "기준 피처 위에 이 묶음을 더했을 때의 개선 효과". 피처 간 정보가 겹치므로 개별 변수의 독립 기여로 단정하지 않음
- 같은 fold 재검증은 조건을 맞춘 비교용일 뿐, 튜닝·선택으로 생긴 낙관성을 없애지 못함 → train 사상 15%(약 18개)를 홀드아웃으로 떼어두고, **개인은 열지 않으며** 팀 최종 조합 1개를 재혁이 한 번만 확인
- early stopping을 검증 fold로 하므로 OOF는 약간 낙관적
- "소수 대형 사상이 Global RMSE를 좌우한다"는 다른 참가자의 Q&A 분석(상위 5개 사상이 오차제곱합 52.6%)에 근거한 것. **우리 OOF로 직접 확인**한 뒤 판단하고, 큰 상승 구간만 개선하다 다른 구간을 떨어뜨리지 않는지 전체 RMSE와 사상별 오차를 함께 봄
- 목적함수는 기본 MSE(평가가 RMSE이므로)

## 4. Git 협업 방식
- 팀 레포: `DGU-BAF/BAF-26-2-society_2` (수아 PC remote 이름 `upstream`)
- 수아 포크: `choosooa/BAF-26-2-society_2` (remote 이름 `origin`)
- **커밋·push는 수아가 직접 한다.** Claude는 파일 수정까지만.

### 흐름: 재혁 공통 구조 업로드 → 각자 브랜치·노트북 작업 → PR로 통합 → 최종 실행 확인
1. **공통 구조 먼저**: 재혁이 폴더 구조·공통 베이스라인·`.gitignore`를 main에 올린다. 각자 받은 뒤 브랜치 생성
   ```
   git switch main
   git pull upstream main
   git switch -c feature/suah-feature-exp
   ```
   이후에는 각자 자기 브랜치에 순서 없이 push하고 PR을 올림. main 머지는 재혁이 확인하면서 진행
2. **사람별 노트북**: 같은 노트북을 고친다고 무조건 충돌하진 않지만, 출력·메타데이터까지 바뀌어 충돌 해결·변경 확인이 까다로움 → 사람별 파일로 분리
3. **fold는 공유 파일로 통일**: 노트북마다 fold를 따로 만들지 않고, 재혁이 확정한 `row_id`·`event_id`·fold 매핑과 홀드아웃 목록을 받아 씀. 정렬·처리 차이로 분할이 달라지는 걸 막기 위함
4. **피처 전달은 코드까지**: 한동에게 ① 채택 피처 목록(`final_features.json`) ② 피처 생성 함수 또는 노트북 코드 ③ 비교 결과·기준 파라미터를 같이 전달
5. **11/3 `.py` 전환은 필수 아님**: 중복 핵심 함수만 필요한 만큼 분리. 처음부터 끝까지 돌아가는 최종 노트북 하나를 확보하는 것도 현실적인 방법

### 폴더 구조
```
repo/
├─ README.md
├─ CLAUDE.md
├─ docs/
├─ data/                      # .gitignore (대회 원본은 각자 공식 사이트에서 받기)
├─ notebooks/
│  ├─ 00_baseline.ipynb       # 공통 (재혁 관리) ← hou_baseline_v1.ipynb
│  ├─ eda_ver1.ipynb
│  ├─ suah_feature_exp.ipynb  # ← hou_feature_exp_v1.ipynb
│  ├─ handong_tuning.ipynb
│  └─ jaehyuk_pipeline.ipynb
└─ outputs/                   # 작은 결과만 커밋 (summary csv, json)
```
노트북의 데이터 경로는 실행 위치에서 `data/`를 찾고 없으면 상위 폴더를 봄 → 레포 루트·`notebooks/` 어디서 실행해도 동작. README에도 명시.

### 올리기 전 체크
- `data/`는 올리지 않음
- OOF CSV는 파일당 약 22MB(GitHub 파일 한도 100MB) → 공유 드라이브. git에는 `experiment_summary.csv`, `final_features.json` 같은 작은 결과만 (`.gitignore`에 반영됨)
- 노트북 출력은 지우고 커밋 (`nbstripout` 권장)

### 기준 모델 오차 분석 (dev OOF 0.2182, 10/30)
- 공통 fold(`outputs/common/event_folds.csv`)가 1차 실험 분할과 같음을 확인 (fold RMSE 반올림 차이 이내)
- 정답 > 0.5 m 행은 전체의 5.8%인데 오차제곱합의 71.5%. 구간이 클수록 과소예측 (0.5–1 m: 평균 −0.24, 1–2 m: −0.59, 2 m 초과: −0.84)
- "아직 수위가 정체(dwl_1h ≤ 0.05)인데 곧 0.5 m 넘게 오르는 행"이 3.3%인데 오차제곱합의 43.5%. 평균 정답 1.29 vs 예측 0.76. 이 행들은 강우가 이미 있음(imerg 6h 평균 13.7 vs 전체 7.5) → **상승 시작 시점**을 못 잡는 게 핵심
- 상위 5개 사상이 58.1%(TR_E097 혼자 24.9%). 사상 안에서 상위 5개 관측소 비중은 8~27% → 특정 관측소 문제가 아니라 **사상 전체에서 동시에** 틀림
- 관측소 집중도 낮음: 상위 10개 관측소 11.8%

### 팀 EDA에서 나온 참고 사항
- `wl_t_minus_Xh` 컬럼은 이전 행에서 그대로 재현됨 (대체값 없음)
- train 행의 약 63%는 이후 6시간 행이 모두 존재 → 미래 행을 쓰는 피처는 곧바로 누수
- 경과시간과 target의 상관은 24시간 누적강우로 조건부를 걸면 대부분 사라짐
- 주최측이 준 다중 데이터 소스 자체를 기여로 주장하기는 약함 → 소스별 ablation 비교로 근거를 만드는 편이 좋음 (베이스라인 노트북 5-2)
